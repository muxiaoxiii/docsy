# Docsy UI 重构与接口接入方法

## 目标

Docsy 是本地文档工作台，不是工具按钮集合。界面应先让用户看清当前材料、规则、预览和输出，再由后端命令执行确定的处理计划。

现有问题不是单个页面不够美观，而是每个视图各自决定布局、滚动和处理中状态，导致文件一多就出现不可见列表、多个滚动条或操作按钮被挤出可视区域。

## 先画 UI，再接接口的实际做法

1. 先写完整任务流：导入、检查、调整、预览、执行、查看输出和失败恢复。
2. 为每个任务流准备固定样例数据，不连接 Tauri 命令也能展示空列表、普通列表、100 个文件、错误、处理中和完成状态。
3. 在样例数据上定好版式、交互、滚动区域和按钮位置，再定义前后端请求/响应的数据结构。
4. 视图只调用 composable 暴露的状态和动作；composable 再选择 mock 数据或 Tauri IPC。页面不直接承担所有业务逻辑。
5. 对关键页面在桌面最小窗口和常用窗口截图验收，最后才接入真实文件和长任务。

这样不是先做一张静态图，而是先固定可交互的界面状态，再替换数据源。真实接口失败、数据量变大或后台任务变慢时，界面仍然保持可用。

## 全局布局约束

- 应用壳层固定：左侧主菜单、顶部标题、右侧主内容区。
- 每个一级路由只能有一个页面级纵向滚动容器。
- 列表、表格、缩略图等大数据区域可以有内部滚动，但必须有明确高度，且不能把页面操作按钮放在该滚动区域里。
- 导入、输出位置和执行按钮属于工作区工具栏/页脚，始终可见。
- 预览区保持稳定尺寸；页数、文件名和规则变化不能让预览区跳动。
- 每个可执行操作都必须有：空状态、处理中、成功、部分失败、可重试五种可见状态。

## 可复用界面单元

后续页面不应重复实现以下结构：

| 单元 | 责任 |
| --- | --- |
| `ToolWorkspaceShell` | 标题、说明、顶部工具栏、可滚动主体、固定操作区 |
| `FileQueuePanel` | 导入、数量、自然排序、可滚动文件列表、删除/清空、单项状态 |
| `OutputTargetControl` | 输出目录、默认命名、打开输出位置 |
| `AsyncTaskStatus` | 处理中进度、取消、成功/失败摘要和重试 |
| `DocumentPreviewPanel` | 预览加载、翻页、缩放、渲染失败和空预览 |
| `RuleFormPanel` | 规则编辑、即时示意、真实预览和校验提示 |

这些组件只负责展示和用户交互，不包含 qpdf、FFmpeg、模板或文件系统命令。

## 数据与接口边界

每个工具保留一个同样形状的视图模型。示例：

```ts
type FileQueueItem = {
  id: string
  path: string
  name: string
  status: 'ready' | 'processing' | 'done' | 'failed'
  message?: string
}
```

页面通过 composable 读取 `items`、`isRunning`、`summary` 和 `run()`；真实模式调用 Tauri，演示/测试模式读取 fixture。这样 UI 修改不需要修改 Rust 命令，Rust 返回结构变化也能在 composable 层被明确处理。

## 分模块落地顺序

1. PDF 基础工具：解锁、合并、提取、压缩和拆分先统一为 `ToolWorkspaceShell + FileQueuePanel`。合并和解锁的长列表已先修正为独立滚动，后续迁入共享组件。
2. 证据处理：统一文件清单、检测状态、规则编辑、预览和输出结果，不让合并/拆分页面复刻另一套列表。
3. 图片排版和视频抽帧：复用文件队列、预览、输出位置和后台任务状态。
4. 模板模块：保留现有业务能力，但拆出模板库、字段制作、填写、历史记录四个工作区，避免单一巨型页面继续膨胀。

## 验收基线

- 100 个文件时能看见文件数量、滚动列表和执行按钮。
- 2000 页 PDF 的处理中状态不遮挡操作区域，用户知道当前阶段和可以等待的原因。
- 窗口为最小尺寸时没有内容被裁切，也不会出现两个功能相同的纵向滚动条。
- 导入、处理中、失败和完成状态均有视觉验收截图。
- 所有模块使用同一套状态枚举，显示文字可以中文，但内部状态不依赖中文字符串。
